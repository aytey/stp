# Recursive call cycles that walk an AST-shaped graph, which is how a pass
# ends up using call stack in proportion to how deeply the input nests. This
# includes indirect and mutual recursion, AST containers, and self-linked
# mutable graphs derived from an AST even when their walkers no longer take
# an ASTNode parameter.
# scripts/check-ast-recursion.py fails when one appears that is not listed
# here, so that adding a recursive walk is a decision someone made rather
# than one that slipped through.
#
# Format: Name: status: reason
#
# The status is one of seven, and the checker rejects anything else, so a new
# line has to commit to one rather than describing itself freely:
#
#   safe       not a walk over the input at all -- usually an overload
#              forwarding to one -- or bounded by something that is not the
#              input's depth.
#   bounded    it does recurse, but its memo is filled from the bottom up
#              before it runs, so it stops one level down.
#   partial    the recursion is gone on the paths that have been measured,
#              and the shape that still reaches it is named on the line.
#   by-choice  input-depth recursive on purpose. Either it is opt-in and has
#              a disabled case in DeepDag_Test.cpp, or it is on by default
#              and the line says what breaks it.
#   off-path   input-depth recursive, but nothing a solve does reaches it:
#              dead code, an assert, a printer behind a flag, a build-time
#              tool. The line says which, because that is the whole claim.
#   on-path    input-depth recursive on a path a solve takes, and not
#              converted. The line says the depth it was measured to die at,
#              so these can be ordered by how close that is to real input.
#   unaudited  predates this check. Nobody has looked.
#
# Being on this list is NOT a claim that a function is safe. Nothing is
# "unaudited" any more, but 19 are "on-path", which means someone looked and
# found a recursion a solve can reach and did not convert it. Read the
# status, not the presence of the name.
#
# The audit asked reachability before depth, on the evidence that "recursive"
# and "reachable" are not the same question: BVTypeCheckRecursive sat here
# looking like the next thing to convert, and turned out to be reached by
# nothing but a disabled tool's assertions, while the type check every solve
# runs is per-node.
#
# The on-path ones carry a measured depth where anyone has measured one, and
# say so where nobody has. That is the order to work in, and it has not once
# been the order the names suggest: the first wall found on the near side of
# real input was reached through a pass already marked "partial", and the two
# with the most alarming names need ten times the depth of anything we have.
# Each conversion has revealed the next one behind it -- the simplifier's
# formula arms hid FpTotalise, which hid SplitExtracts::buildMap, which is
# where `gen.py fp-add` stops today, at 60,000.
#
# The parsing is crude, so some of these are not walks at all -- an overload
# forwarding to another overload reads the same from outside. Those say so.
