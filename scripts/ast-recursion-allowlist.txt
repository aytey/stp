# Functions that take an AST node and call themselves, which is how a pass
# ends up using call stack in proportion to how deeply the input nests.
# scripts/check-ast-recursion.py fails when one appears that is not listed
# here, so that adding a recursive walk is a decision someone made rather
# than one that slipped through.
#
# Format: Name: status: reason
#
# The status is one of seven, and the checker rejects anything else, so a new
# line has to commit to one rather than describing itself freely:
#
#   safe       not a walk over the input at all -- usually an overload
#              forwarding to one -- or bounded by something that is not the
#              input's depth.
#   bounded    it does recurse, but its memo is filled from the bottom up
#              before it runs, so it stops one level down.
#   partial    the recursion is gone on the paths that have been measured,
#              and the shape that still reaches it is named on the line.
#   by-choice  input-depth recursive on purpose. Either it is opt-in and has
#              a disabled case in DeepDag_Test.cpp, or it is on by default
#              and the line says what breaks it.
#   off-path   input-depth recursive, but nothing a solve does reaches it:
#              dead code, an assert, a printer behind a flag, a build-time
#              tool. The line says which, because that is the whole claim.
#   on-path    input-depth recursive on a path a solve takes, and not
#              converted. The line says the depth it was measured to die at,
#              so these can be ordered by how close that is to real input.
#   unaudited  predates this check. Nobody has looked.
#
# Being on this list is NOT a claim that a function is safe. Nothing is
# "unaudited" any more, but 21 are "on-path", which means someone looked and
# found a recursion a solve can reach and did not convert it. Read the
# status, not the presence of the name.
#
# The audit asked reachability before depth, on the evidence that "recursive"
# and "reachable" are not the same question: BVTypeCheckRecursive sat here
# looking like the next thing to convert, and turned out to be reached by
# nothing but a disabled tool's assertions, while the type check every solve
# runs is per-node.
#
# Of the 21 on-path, four carry a measured depth and the rest say they do
# not. Nearest to real input by a wide margin is the formula recursion on the
# Simplifier::SimplifyTerm line: a chain of fp.add 8,000 deep is a valid
# query that dies in it today, against the ~9,300 of the deepest input we
# have. Everything else measured needs 40,000 or more. That is the order to
# work in, and it is not the order the names suggest.
#
# The parsing is crude, so some of these are not walks at all -- an overload
# forwarding to another overload reads the same from outside. Those say so.

AIGSimplifyPropositionalCore::convert: off-path: walks the AIG the pass built, one frame per level of it, but the pass is behind --enable-aig-core-simplify (STP.cpp asks UserFlags.enable_aig_core_simplify)
AIGSimplifyPropositionalCore::theoryToFresh: off-path: same pass, same flag; this half walks the AST rather than the AIG
ArrayTransformer::assertTransformPostConditions: off-path: its one call site is inside an #if 0
BVTypeCheckRecursive: off-path: nothing in the library calls it. The type check a solve runs is BVTypeCheck, which is one node -- 143 call sites, neither of its two helpers descends. This one is reached only from four asserts in tools/rewrite_rule_gen, which needs BUILD_EXTRA_TOOLS (default OFF) and is compiled out under NDEBUG anyway. Dies at 300,000 if called directly
BitBlaster::BBForm: bounded: both memos primed by one walk before either runs (primeMemos)
BitBlaster::BBTerm: bounded: both memos primed by one walk before either runs (primeMemos)
BitBlaster::buildAdditionNetworkResult: safe: two overloads sharing a name. The one that looks recursive loops over the bit width calling the other, so it is bounded by the word size and not by the input
BitBlaster::updateTerm: safe: recurses to a fixed point on one node, not down the DAG
CommonSubSum::rebuild: off-path: behind --enable-common-subsum (UserFlags.enable_common_subsum, default false). DeepDag's deep_common_sub_sum runs the pass at 20,000 and passes
ConstantBitPropagation::checkAtFixedPoint: off-path: its one caller is an assert in BitBlaster, so it is gone under NDEBUG; in an assertions build it does walk the input

ExtensionalityContext::lowerArrayEqualities: safe: overload forwarding, not a walk
FindPureLiterals::build: on-path: enable_pure_literals defaults true, and this walks the formula for each literal's polarity one frame per level, memoised on nodeToPolarity. Depth not measured
FlattenKindNoDuplicates: on-path: FlattenKind(AND/OR/BVAND/BVOR) reaches it from the simplifier, the BV solver, PropagateEqualities, MergeSame and UseITEContext, and it walks a nested same-kind chain one frame per level. Measured to die between 100,000 and 150,000 at 8 MiB, and at 20,000 at 1 MiB. No parsed query gets there: the simplifying factory flattens an AND as it builds it, so the nested node never exists -- a 200,000-deep nested AND answers sat. A pass building with the hashing factory would reach it
FloatBlast::asPacked: on-path: float lowering, one frame per level of a float expression, cached per node. Not measured, and not measurable from a query yet: FpTotalise::visit walks the same expression first and dies before it
FloatBlast::asUnpacked: on-path: as FloatBlast::asPacked -- same pass, same unmeasured reason
FloatBlast::comparisonLeaf: on-path: as FloatBlast::asPacked -- same pass, same unmeasured reason

FloatBlaster::canonicalBits: safe: overload forwarding, not a walk
FloatBlaster::operandFormat: safe: overload forwarding; the walk it calls looks at one node's children
FpTotalise::collectRoundingModeTerms: on-path: collects the rounding-mode terms a totalised float expression constrains, one frame per level, over the same expression FpTotalise::visit walks
FpTotalise::visit: on-path: totalises float operations before lowering, one frame per level, with a persistent cache. Measured on a chain of fp.add: 20,000 solves, 40,000 dies here. With the simplifier on, that query dies earlier still -- between 7,000 and 8,000, in the formula recursion named on Simplifier::SimplifyTerm below, which is the nearest wall to real input this list has
GDL_Print: off-path: the GDL printer, behind --print-back-GDL (UserFlags.print_STPinput_back_GDL_flag)

One caller: the boolean-symbol arm of model evaluation, asking whether a symbol occurs in the value the model recorded for it. Depth not measured; a recorded model value is a constant in every corpus query
STPMgr::arrayBaseSymbol: on-path: iterative down a write chain, and recursive only into the two branches of an array if-then-else, so its depth is how deeply those nest. Depth not measured
Simplifier::CombineLikeTerms: safe: overload forwarding, not a walk
Simplifier::SimplifyArrayTerm: on-path: descends an array term's base array and both branches of an array if-then-else, one frame per level. Not measured: a 200,000-deep store chain dies in numberOfReadsLessThan before reaching it
Simplifier::SimplifyTerm: partial: map primed before it runs (primeTerms), through children and through the substitution image -- but a term below a BOOLEAN operand is handed to SimplifyFormula and not primed, and still recurses. Measured: a chain of fp.add 8,000 deep dies there, 7,000 solves. The frames are SimplifyFormula -> simplifyNonAndOr -> SimplifyIteFormula or SimplifyNotFormula -> SimplifyFormula, which is mutual and so invisible to this check -- the AND/OR driver was converted, these arms were not. At ~8,000 this is the nearest thing on the list to the ~9,300 of the deepest input we have, and the next conversion to do
Simplifier::checkIfInSimplifyMap: off-path: a debug check whose one caller is commented out
SimplifyingNodeFactory::CreateSimpleAndOr: safe: overload forwarding -- the binary form puts its two operands in a vector and calls the vector form
SplitExtracts::buildMap: on-path: enable_split_extracts defaults true, and this walks the input for extracts over symbols one frame per level, guarded by a visited set. Depth not measured
StrengthReduction::replace: on-path: rebuilds children one frame per level, cache-guarded, on the substitutions the analysis found. The enabled deep_strength_reduction case runs the pass at 20,000
SubstitutionMap::applySubstitutionMapUntilArrays: safe: overload forwarding, not a walk

Measured to die between 80,000 and 100,000 at 8 MiB, and at 20,000 at 1 MiB -- roughly ten times the deepest corpus input
